# React/FastAPI Product UI Migration Plan

## Purpose

This staged plan is the handoff document for future work on the `react-fastapi-product-ui` branch. The goal is to migrate from a Streamlit MVP to a product-like FastAPI + React interface while preserving the current RAG system, retrieval comparison logic, evaluation pipeline, and offline-first tests.

The Streamlit app remains the stable backup. FastAPI and React are added as a productized interface layer, not as a replacement for the existing RAG core.

## Product Direction

The application should be a RAG-based study assistant and retrieval-method comparison workbench, not a generic LLM chatbot.

Core product behavior:

* users upload or select study materials;
* users ask questions in a clean chat interface;
* the backend retrieves chunk-level evidence using BM25, dense retrieval, hybrid fusion, and reranking;
* the answer is generated from a grounded prompt using the selected evidence;
* inline citations such as `[E1]` appear directly after supported claims;
* the right panel explains evidence, retrieval flow, method comparison, latency, and evaluation metrics.

## Stage 1: FastAPI Backend Layer

Add a FastAPI interface over existing services.

Target endpoints:

```text
GET  /api/health
GET  /api/status
GET  /api/documents
POST /api/documents/upload
DELETE /api/documents/{doc_id}
POST /api/query
GET  /api/evaluation/summary
POST /api/evaluation/run
```

Rules:

* FastAPI wraps current `src/rag_project` services;
* no RAG algorithm rewrite;
* no Chroma, LangChain, Docker, ASR/TTS, or vector database in this stage;
* first implementation returns JSON, not streaming SSE;
* tests use FastAPI `TestClient` and do not require API keys or network.

Implementation status:

* `src/rag_project/api/main.py` adds a JSON-first FastAPI app factory and default `app`;
* app factory accepts injectable registry/upload/cache/report paths for isolated tests;
* `python scripts/dev.py api` starts `uvicorn rag_project.api.main:app`;
* query responses expose `answer.text`, `citations`, `final_evidence`,
  `retrieval_trace`, `retrieval`, `timing`, `scope` and `diagnostics`;
* upload, document deletion, query and evaluation endpoints reuse existing
  app services and evaluation modules instead of rewriting RAG logic;
* Streamlit remains available as the backup UI.
* Stage 1 is verified by FastAPI endpoint tests and the full offline test suite.

Stage 1 environment note:

`environment.yml` now includes `fastapi`, `uvicorn`, `python-multipart` and
`httpx`. Existing environments must be updated before running the new API
tests.

## Stage 2: Prompt-Driven Grounded Answer Contract

The backend answer should be generated by a grounded prompt, not by raw retrieval-result concatenation.

Rules:

* Top-k final evidence is injected into a prompt builder;
* retrieved context is explicitly marked as untrusted reference material;
* the model must answer only from evidence;
* insufficient evidence must be stated clearly;
* prompt injection inside documents must not be followed;
* mock LLM remains deterministic for tests and no-key fallback.

Implementation status:

* prompt evidence blocks are labeled as `[E1]`, `[E2]`, `[E3]`;
* prompt instructions require natural-language answers with inline citation
  markers directly after supported claims;
* mock local LLM output is deterministic natural language with inline markers,
  not raw chunk concatenation;
* QueryService no longer appends a trailing `References:` block for grounded
  answers;
* `/api/query` answer text now contains inline markers that map to
  `citations[].evidence_id` and `final_evidence[].evidence_id`;
* SiliconFlow prompt instructions request the same inline citation pattern and
  still fall back to the mock client on API failure.

Recommended query response shape:

```json
{
  "answer": {
    "text": "Hybrid retrieval improves coverage by combining lexical and dense signals [E1]. Reranking then prioritizes the most relevant chunks [E2].",
    "style": "detailed",
    "grounding_status": "grounded"
  },
  "citations": [
    {
      "evidence_id": "E1",
      "chunk_id": "chunk-001",
      "doc_id": "doc-lecture-01",
      "source_file": "lecture01.pdf",
      "page": 3
    }
  ],
  "final_evidence": [],
  "retrieval_trace": {},
  "timing": {},
  "scope": {}
}
```

## Stage 3: React Three-Panel Product UI

Use Vite + React as the recommended product frontend. TypeScript is preferred for API contract safety.

Required layout:

```text
Left: Knowledge Base
Center: Chat
Right: Evidence Intelligence
```

Left panel:

* upload PDF/TXT/MD files;
* list uploaded documents;
* select retrieval scope;
* support all documents and selected documents only;
* show chunk count, document type summary, ingestion status, and RAG enabled state.

Center panel:

* full-height bounded chat layout;
* scrollable message area;
* fixed input area;
* natural language answers;
* inline citation anchors directly after supported claims.

Right panel:

* cited evidence cards labeled `E1`, `E2`, `E3`;
* source file, page, chunk id, chunk type, method, score, and preview;
* retrieval flow: BM25 -> Dense -> Fusion -> Reranker -> Final Evidence;
* BM25/Dense/Fusion/Reranker method comparison;
* score bars, latency badges, and method contribution summary;
* collapsible evaluation metrics and diagnostics.

Citation behavior:

* `[E1]` appears inside the answer text after the supported sentence;
* React renders `[E1]` as an inline anchor;
* clicking `[E1]` scrolls to and highlights Evidence E1 in the right panel;
* if scrolling fails, answer text and citation markers remain readable.

## Stage 4: Evaluation Visualization

Evaluation should support the data science assessment without dominating the product UI.

Rules:

* Recall@k, MRR, NDCG, latency, and error cases are integrated into the right panel;
* show metrics with visual bars, small cards, or compact charts rather than raw numbers only;
* keep raw debug tables and error cases collapsed by default;
* preserve reproducible offline evaluation.

## Stage 5: Demo Packaging

Final delivery should include:

* README instructions for FastAPI and React startup;
* Streamlit fallback instructions;
* demo script covering upload, scope selection, question answering, inline citations, evidence inspection, method comparison, and evaluation metrics;
* limitations and fallback notes;
* API smoke-test instructions for SiliconFlow without committing secrets.

## Testing Expectations

Future implementation must include:

* FastAPI `TestClient` tests for health, status, documents, upload, query, and evaluation endpoints;
* React tests with mocked API responses for upload state, material selection, query, inline citation click, and evidence highlight;
* existing RAG unit tests must continue to pass;
* default tests must not access network, require API keys, use GPU, or download models;
* live SiliconFlow checks remain optional smoke tests only.

## Out Of Scope Until Explicitly Approved

* deleting the Streamlit backup;
* rewriting retrieval algorithms;
* introducing Chroma, LangChain, Docker, ASR/TTS, cloud vector databases, or persistent multi-user auth;
* copying frontend_reference code directly;
* making the product a generic LLM chatbot without evidence and retrieval comparison.
